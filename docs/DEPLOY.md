# Deploying Shop Nest (free tier: Render + Neon)

The setup is described in [`render.yaml`](../render.yaml) (a Render "Blueprint"). It has **not**
been deployed: this page lists what to do, in order, when you decide to.

```
browser ──https──▶ shop-nest-web (Render, free) ──/api/*──▶ shop-nest-api (Render, free) ──▶ Neon PostgreSQL 18 (free)
```

**Why Neon:** Render allows one free database per workspace, and node-learning's `ecommerce-db`
already uses it. The two projects must **never share a database**: they have tables with the
same names (`orders`, `payments`, `coupons`...) and both run a job queue in a `pgboss` schema.

**What "free" means here:**
- Both Render services **sleep after ~15 minutes** without visits; the next visit wakes them
  (about a minute). While the API sleeps, scheduled jobs (expiring unpaid orders, payment
  reconciliation) pause; on waking they run once to catch up.
- Neon's free compute **suspends** when nothing is connected, and resumes on the next query
  (a second or so). The free plan has monthly compute and storage limits (1 GB per project):
  check Neon's current numbers on its pricing page.
- Fine for a demo shop and for learning; see "Upgrading later" for a real launch.

## Before you start

| You need | Used for |
|---|---|
| A Render account connected to the GitHub repository | the two services |
| A Neon account | the database |
| A Brevo account, an API key, a verified sender address | `BREVO_API_KEY`, `EMAIL_FROM_ADDRESS` |
| Razorpay **test** keys: the SAME ones node-learning uses are fine | `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET` |

Copy secrets **by hand into the dashboards**, never into a file in either project.
`JWT_SECRET` is generated by Render: never reuse node-learning's.

## Steps

1. **Push** `main` and wait for CI to be green (both jobs: the second one builds and starts the
   Docker images).
2. **Neon**: create a project named `shop-nest`, region **AWS Asia Pacific (Singapore)**,
   **Postgres 18** (the default; the app needs 18). Copy the **direct** connection string:
   in "Connect", turn **Connection pooling off** (the host has no `-pooler` in it). The job queue
   listens for new jobs and Prisma's migrations need a real session, which a pooler can't give.
3. **Render**: **New → Blueprint**, pick the repository. It shows `shop-nest-api` and
   `shop-nest-web`. Fill in the secrets it asks for (`sync: false` entries):
   - `DATABASE_URL`: the Neon string from step 2
   - `BREVO_API_KEY`, `EMAIL_FROM_ADDRESS`
   - `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`: the same values node-learning uses
   - `RAZORPAY_WEBHOOK_SECRET`: leave it for step 7
   - `SENTRY_DSN`: optional, empty = off
4. **Apply**. Render builds both images. The API applies the migrations when it starts
   (`MIGRATE_ON_START=true` → `apps/api/scripts/start.sh`), then serves.
5. **Addresses**: if Render gave the services different addresses than the ones in
   `render.yaml` (it adds a suffix when a name is taken), set `WEB_ORIGIN` on the API to the
   web's address and `API_URL` on the web to the API's address, and redeploy the web service
   (`API_URL` is used while building it).
6. **Check**: open `https://<web address>/robots.txt`, then the home page. In the API's logs,
   the request lines should show visitors' real IP addresses. If every line shows the same
   address, the number of trusted proxy hops is wrong: try `TRUST_PROXY` = `3` and check again
   (rate limits are per IP, so this matters).
7. **Razorpay webhook** (Dashboard → Settings → Webhooks → **Add New Webhook**: this is a
   SECOND webhook, node-learning keeps its own): URL `https://<web address>/api/webhooks/razorpay`,
   events `payment.captured`, `payment.failed`, `order.paid`, `refund.processed`,
   `refund.failed`. Copy **its** secret into `RAZORPAY_WEBHOOK_SECRET` on the API service.
   Events about node-learning's payments may arrive here too: shop-nest acknowledges and
   ignores Razorpay orders it didn't create.
8. **First admin**: sign up on the live shop, then from your computer, with the Neon
   connection string (in the command only, never in a file):
   ```bash
   cd apps/api
   DATABASE_URL="<neon connection string>" npx tsx scripts/make-admin.ts you@example.com
   ```
9. **Test a real order** with Razorpay's test UPI or cards: the confirmation email should
   arrive; refund it from `/admin`. Switch to live keys only after that, on BOTH projects at
   once if they share the account.

## Without the Blueprint (if Render asks for payment)

The Blueprint is a shortcut; creating the two services by hand gives the same result. In
Render: **New → Web Service** → the repository. Create the **API first** (the web service
needs its address).

| Field | shop-nest-api | shop-nest-web |
|---|---|---|
| Language | Docker | Docker |
| Region | Singapore | Singapore |
| Root directory | (empty: the repository root) | (empty) |
| Dockerfile path | `./apps/api/Dockerfile` | `./apps/web/Dockerfile` |
| Docker build context directory | `.` | `.` |
| Instance type | Free | Free |
| Docker command (Advanced) | (empty: the image knows how to start) | (empty) |
| Health check path (Advanced) | `/api/health` | `/robots.txt` |

Environment variables:
- **shop-nest-api**: `PORT`=`4000`, `MIGRATE_ON_START`=`true`, `DATABASE_URL` (Neon, direct), `JWT_SECRET` (Generate),
  `METRICS_TOKEN` (Generate), `WEB_ORIGIN` (the web's address), `TRUST_PROXY`=`2`,
  `EMAIL_TRANSPORT`=`brevo`, `BREVO_API_KEY`, `EMAIL_FROM_ADDRESS`, `RAZORPAY_KEY_ID`,
  `RAZORPAY_KEY_SECRET` (and `RAZORPAY_WEBHOOK_SECRET` after step 7)
- **shop-nest-web**: `PORT`=`4100`, `API_URL` (the API's address, e.g.
  `https://shop-nest-api.onrender.com`). It's used while BUILDING: after changing it, redeploy.

Then continue with steps 6–9 above.

## Optional

- **Demo catalog**: `DATABASE_URL="<neon connection string>" npm run db:seed -w @shop/api`
  from your computer. Don't run `db:seed-sales` on a real shop: it invents orders.
- **Monitoring**: see "Observability" in the README.

## Upgrading later (paid)

For a real launch, move to paid instances, which allow the safer layout:
- the API as a **private service** (`type: pserv`), reachable only by the web service over
  Render's private network; the web's `API_URL` then comes from
  `fromService: { type: pserv, name: shop-nest-api, property: hostport }` and the API's
  `TRUST_PROXY` becomes `uniquelocal`
- migrations as a `preDeployCommand: npx prisma migrate deploy` (a failed migration then stops
  the release instead of the API), and no `dockerCommand`
- services that don't sleep, so scheduled jobs run on time
- a paid database (Neon or Render) with backups you've tested restoring

## Rolling back

Render keeps previous deploys: **Manual Deploy → Rollback** on a service. Migrations aren't
rolled back automatically, which is why each one in this project only ever *adds* (new tables,
columns with defaults): the previous version of the code still works with the newer schema.
Neon can also restore the database to an earlier moment (within its free history window).
